1. Overview

Objective

The aim of this task is to build a simple IoT system using an ESP32 that hosts a web server and allows a user to control an LED from a web browser over Wi-Fi.

Problem Being Addressed

An LED connected to a microcontroller is usually controlled by a physical switch or by programmed logic. This project shows how the same LED can be switched on and off remotely through a browser without using a physical button.

Project Summary

In this project, the ESP32 connects to a Wi-Fi network and acts as a small web server. When a user enters the ESP32's IP address into a browser, a simple HTML page appears with ON and OFF buttons. Pressing a button sends an HTTP request to the ESP32, which then updates the LED state accordingly.

Browser → Wi-Fi → ESP32 Web Server → GPIO → LED

2. Concepts

ESP32 Web Server

The ESP32 is a Wi-Fi-enabled microcontroller that can act as a small web server. It can receive HTTP requests from devices connected to the same network and respond with HTML content.

The ESP32 performs two main functions in this project:

  • Hosts the HTML webpage.
  • Controls the LED according to commands received from the browser.

Wi-Fi Communication

The ESP32 connects to a Wi-Fi network using its built-in Wi-Fi module. After connecting, it obtains an IP address from the network. The user enters this IP address into a web browser, which communicates with the ESP32 using HTTP.

HTTP Request

When the user clicks the ON or OFF button, the browser sends an HTTP request to the ESP32.

  • /LED=ON turns the LED on.
  • /LED=OFF turns the LED off.

The ESP32 reads the requested path and changes the GPIO output.

HTML Interface

HTML is used to create the control webpage. The webpage contains buttons that allow the user to send commands to the ESP32.

3. System Design

System Architecture

The complete system consists of four main stages:

User → Web Browser → Wi-Fi Network → ESP32 → LED

Data Flow

  1. The ESP32 connects to the Wi-Fi network.
  2. The ESP32 starts a web server.
  3. The ESP32 receives an IP address.
  4. The user enters the IP address in a browser.
  5. The ESP32 sends the HTML control page to the browser.
  6. The user clicks the ON or OFF button.
  7. The browser sends an HTTP request to the ESP32.
  8. The ESP32 processes the request.
  9. The ESP32 changes the LED GPIO state.
  10. The LED turns ON or OFF.

5. Wiring / Setup

The LED is connected to a digital GPIO pin of the ESP32 through a current-limiting resistor.

Circuit Operation

  • When the ESP32 GPIO is set to HIGH, the LED turns ON.
  • When the ESP32 GPIO is set to LOW, the LED turns OFF.
  • A resistor is used with the LED to limit the current and protect the LED and GPIO.

Note: If the physical setup uses the ESP32's built-in LED instead of an external LED, the wiring section can be modified to state that no external LED wiring was required.

6. Implementation

Program Logic

  1. Define the Wi-Fi network credentials.
  2. Initialize the LED GPIO.
  3. Connect the ESP32 to Wi-Fi.
  4. Start the web server.
  5. Wait for an HTTP request from the browser.
  6. Identify whether the request is for LED ON or LED OFF.
  7. Change the GPIO output.
  8. Return the updated HTML webpage to the browser.

Complete ESP32 Source Code

#include <WiFi.h>

const char* ssid = "YOUR_WIFI_NAME";
const char* password = "YOUR_WIFI_PASSWORD";

WiFiServer server(80);
const int ledPin = 2;

void setup() {
  Serial.begin(115200);
  pinMode(ledPin, OUTPUT);
  digitalWrite(ledPin, LOW);

  WiFi.begin(ssid, password);
  Serial.print("Connecting to Wi-Fi");

  while (WiFi.status() != WL_CONNECTED) {
    delay(500);
    Serial.print(".");
  }

  Serial.println();
  Serial.println("Wi-Fi connected");
  Serial.print("ESP32 IP Address: ");
  Serial.println(WiFi.localIP());
  server.begin();
}

void loop() {
  WiFiClient client = server.available();
  if (!client) {
    return;
  }

  String request = client.readStringUntil('\r');
  client.flush();

  if (request.indexOf("GET /LED=ON") >= 0) {
    digitalWrite(ledPin, HIGH);
  }

  if (request.indexOf("GET /LED=OFF") >= 0) {
    digitalWrite(ledPin, LOW);
  }

  client.println("HTTP/1.1 200 OK");
  client.println("Content-Type: text/html");
  client.println("Connection: close");
  client.println();

  client.println("<!DOCTYPE html>");
  client.println("<html>");
  client.println("<head>");
  client.println("<title>ESP32 LED Control</title>");
  client.println("</head>");
  client.println("<body>");
  client.println("<h1>ESP32 LED Control</h1>");
  client.println("<p>");
  client.println("<a href=\"/LED=ON\"><button>LED ON</button></a>");
  client.println("</p>");
  client.println("<p>");
  client.println("<a href=\"/LED=OFF\"><button>LED OFF</button></a>");
  client.println("</p>");
  client.println("</body>");
  client.println("</html>");

  delay(1);
  client.stop();
}

10. Challenges & Fixes

Challenge 1 — ESP32 Could Not Connect to Wi-Fi

Problem: The ESP32 remained in the Wi-Fi connection loop.

Solution: The Wi-Fi SSID and password were checked and the ESP32 was placed within the Wi-Fi network range.

Challenge 2 — Webpage Could Not Be Opened

Problem: The browser could not access the ESP32 server.

Solution: The IP address printed in the Arduino Serial Monitor was checked, and the computer/mobile device was connected to the same Wi-Fi network as the ESP32.

Challenge 3 — LED Did Not Respond

Problem: The LED did not change state when the button was pressed.

Solution: The GPIO pin configuration and LED wiring were checked. The ON and OFF HTTP request paths were also verified.

Challenge 4 — Incorrect IP Address

Problem: The ESP32's IP address can change when it reconnects to the network.

Solution: The current IP address was read from the Serial Monitor after each Wi-Fi connection.

1. Overview

Objective

The aim of this task was to build a cloud-connected IoT system using an ESP32-C3, Rust firmware, MQTT, and Adafruit IO. A remote dashboard sends commands that the device uses to switch an LED.

Problem Being Addressed

In Task 1, the ESP32 hosted a webpage and the browser generally needed to be on the same local network. This task adds cloud messaging, so a dashboard can send a command through Adafruit IO rather than connecting directly to a device-hosted page.

Project Summary

The ESP32-C3 joins a Wi-Fi network, authenticates with the Adafruit IO MQTT broker, and subscribes to an LED-control feed. The dashboard publishes ON or OFF; the Rust application handles the received payload and updates the configured LED GPIO.

Adafruit IO Dashboard → MQTT Broker → ESP32-C3 (Rust) → GPIO → LED
Platform note: This report describes the ESP32-C3 programmed in Rust. GPIO numbering, the onboard LED, and the Rust HAL/API depend on the exact development board and project configuration.

2. Concepts

Adafruit IO

Adafruit IO is a cloud IoT service for exchanging and visualizing device data. It provides feeds, dashboards, and MQTT access. Here, a dashboard control publishes commands to the LED feed.

MQTT

MQTT (Message Queuing Telemetry Transport) is a lightweight publish/subscribe messaging protocol. A publisher sends a message to a topic, and a broker routes it to clients subscribed to that topic.

MQTT roleRole in this project
PublisherThe Adafruit IO dashboard publishes the selected LED command.
BrokerAdafruit IO receives and routes MQTT messages.
SubscriberThe ESP32-C3 Rust application subscribes to the LED feed.
Feed / topicThe named communication channel carrying the LED command.

Adafruit IO calls its data channels feeds. The MQTT topic for a feed follows the account-specific path username/feeds/bulb-control.

  3. The device subscribes to the account's bulb-control feed.

  5. The dashboard publishes the selected value to the feed.
  6. The broker forwards the message to the subscribed device.

12. Challenges & Fixes

MQTT Connection Failure

Problem: The ESP32-C3 could not connect to Adafruit IO. Checks: Confirm Wi-Fi Internet access, broker hostname, network availability, and MQTT client configuration.

Feed Subscription Mismatch

Problem: The device connected but did not receive dashboard commands. Checks: Verify the account username, feed key, and complete topic path: username/feeds/bulb-control.

Authentication Error

Problem: Adafruit IO rejected the client. Checks: Confirm the account username and current AIO key, and keep the key private.

LED Did Not Respond

Problem: A message arrived but the LED state did not change. Checks: Verify payload decoding, configured ESP32-C3 GPIO, wiring, and whether the board LED is active-high or active-low.

Rust Target or Peripheral Configuration

Problem: Firmware build or GPIO initialization did not match the board. Checks: Confirm the ESP32-C3 Rust target, ESP-IDF/toolchain setup, crate versions, and pin mapping for the specific board.

1. Overview

Objective

This task demonstrates voice-initiated IoT automation. Saying “Hey Siri, switch on light” starts the configured Siri shortcut / IFTTT workflow. IFTTT updates an Adafruit IO feed, and the ESP32-C3 receives that command over MQTT and switches the LED using Rust firmware.

Problem Being Addressed

Dashboard control requires a user to open an app or webpage and operate a control manually. Voice automation makes the interaction hands-free: a spoken phrase starts a cloud workflow that carries the command to the device.

Project Summary

Siri recognizes the configured phrase and invokes the associated shortcut or Applet trigger. IFTTT performs the cloud action that writes the command to the Adafruit IO bulb-control feed. 2. Concepts

IoT Automation

IoT automation connects an event to a device action through a predefined workflow. Instead of manually changing a dashboard control, a voice phrase can initiate the workflow and cause the remote device to respond.

IFTTT

IFTTT means “If This Then That.” An Applet links a trigger (the “This”) to an action (the “That”). In this experiment, a Siri phrase or shortcut starts the configured automation, and its action updates the Adafruit IO feed.

Trigger and Action

IFTTT actionSend the selected command to the Adafruit IO bulb-control feed.
Device responseESP32-C3 receives the MQTT value and updates its LED GPIO.

MQTT

MQTT is a lightweight publish/subscribe protocol. Adafruit IO provides the broker and feed; the Rust application on the ESP32-C3 subscribes to the feed and handles new values.

3. Role of Adafruit IO

Adafruit IO is the cloud handoff between IFTTT and the ESP32-C3. IFTTT updates a feed with the command, while the device receives the new feed value through its MQTT subscription.

Siri / IFTTT action → Adafruit IO → bulb-control feed → MQTT broker → ESP32-C3

When the feed receives ON, the Rust firmware sets the configured LED output to its active state. An OFF value sets it inactive if an off phrase/action is configured.

Dashboard writes mode = auto and threshold → firmware compares averaged light with threshold → relay follows the configured rule

Connection Lost

Wi-Fi / Firebase unavailable → firmware sets relay OFF → dashboard data becomes stale or waiting → reconnect and resume updates

9. Database Structure & Security

The proposed Realtime Database schema keeps owner data shallow and readings ordered by timestamp:

users/<OWNER_UID>/bulb                 false
users/<OWNER_UID>/settings/mode        "manual" | "auto"
users/<OWNER_UID>/settings/threshold   0..4095
users/<OWNER_UID>/readings/<UNIX_TIME> {
  temperature, humidity, light, relay
}
Path / settingPurpose / access
users/<uid>/bulbOwner controls manual bulb command.
users/<uid>/settingsOwner controls mode and 0–4095 threshold.
users/<uid>/readings/<timestamp>Device account writes sensor and relay records; owner reads them.
AuthenticationDashboard uses email/password or Google; firmware uses a separate device identity.

Security Rule Principles

  • Require authentication for all user data.
  • Allow the owner to read their own branch and write their own bulb/settings.
  • Allow the dedicated device identity to read only the configured owner's controls and write readings only under that owner.
  • Validate bulb as Boolean, mode as manual or auto, threshold as a number from 0 to 4095, and reading fields as the expected types.
  • Test allowed and denied access in Firebase Rules Playground before connecting the device.

Do not give the device account broad access to every user's branch. Scope its authorization to the intended owner UID, and never put device passwords or private tokens in dashboard JavaScript.
